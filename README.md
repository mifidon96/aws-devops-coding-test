# AWS DevOps Coding Test — Node.js WebAPI + SQL Server

Terraform templates deploying a Node.js WebAPI to AWS Lambda behind API Gateway, a SQL Server database on RDS, and a GitHub Actions pipeline that accepts future code changes to the API.

## Requirements mapping

| # | Requirement | Where |
|---|---|---|
| 1a | Host/run a Node.js WebAPI | `modules/api` — Lambda + API Gateway HTTP API |
| 1b | SQL Server, standard compute (db.t3.medium) | `modules/database` — RDS, `db.t3.medium` |
| 1c | Both extendable in the future | Discrete modules, typed variables, nothing hardcoded |
| 1d | Deployable to an AWS Lambda function | `aws_lambda_function.api` |
| 1e | CI/CD pipeline accepting future code changes | `.github/workflows/deploy-api.yml` |

## Architecture

```
Internet
   │
   ▼
API Gateway (HTTP API, $default route)
   │
   ▼
Lambda  — VPC-attached, private subnets
   │  │
   │  └──► Secrets Manager (Interface VPC Endpoint — no NAT required)
   ▼
RDS SQL Server Express, db.t3.medium, private subnets, encrypted
```

GitHub Actions assumes an IAM role via OIDC (no stored AWS keys), publishes a versioned artefact to S3, and updates the Lambda's code.

## Key design decisions

**SQL Server Express, not Standard.** The brief specifies `db.t3.medium`. Burstable instance classes are supported only on SQL Server Express and Web editions — Standard and Enterprise require `db.m*`/`db.r*` classes. The instance class in the brief therefore determined the edition. Moving to Standard is a two-variable change, and a `precondition` block catches the invalid combination at plan time.

**Terraform does not own the application artefact.** Terraform packages `app/` on the initial apply so a bare `terraform apply` produces a working API. From then on the pipeline owns the code, and `lifecycle { ignore_changes }` on the artefact fields stops the next apply reverting a deployment.

**No NAT Gateway.** The application's only outbound call is to Secrets Manager, served by an Interface VPC Endpoint. This removes the NAT hourly and data charges and eliminates an internet egress path. `enable_nat_gateway = true` re-introduces it if a future integration needs the public internet — the routes are already wired.

**OIDC, not access keys.** No AWS credentials exist in GitHub. The trust policy is scoped to one repository and one branch — a wildcard would let forks assume the role.

**Credentials never touch Terraform inputs.** The master password is generated by `random_password`, written to Secrets Manager, and read by the Lambda at runtime. It appears in no variable, no tfvars, no pipeline.

## Engine constraints worth knowing

- RDS for SQL Server does not accept `db_name` at creation — databases are created post-provision. Engine limitation, not an omission.
- Express Edition does not support Multi-AZ and caps user data at 10 GB per database. Both guarded by preconditions.

## Deploying

```bash
cd envs/dev
cp terraform.tfvars.example terraform.tfvars   # set github_org
terraform init
terraform plan
terraform apply    # RDS takes 15–25 minutes on first apply
```

Then set GitHub repository variables (Settings → Secrets and variables → Actions → Variables) from the Terraform outputs:

| GitHub variable | Terraform output |
|---|---|
| `AWS_DEPLOY_ROLE_ARN` | `deploy_role_arn` |
| `ARTEFACT_BUCKET` | `artefact_bucket` |
| `LAMBDA_FUNCTION_NAME` | `lambda_function_name` |
| `API_ENDPOINT` | `api_endpoint` |

Verify:

```bash
curl "$(terraform output -raw api_endpoint)/health"      # 200 immediately
curl "$(terraform output -raw api_endpoint)/health/db"   # 503 until first pipeline deploy, then 200
```

`/health/db` returns 503 until the pipeline has bundled the SQL driver (`npm ci`) — the driver is loaded lazily so a missing dependency degrades one route rather than crashing the function.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness — no dependencies |
| GET | `/health/db` | Readiness — proves VPC routing, SGs, credentials |
| GET | `/items` | Read demo rows |
| POST | `/items` | Insert a row. Body: `{"name": "..."}` |

## Known limitations (deliberate, for a dev/test submission)

- `skip_final_snapshot = true`, `deletion_protection = false`, secret recovery window 0 — teardown convenience. All flip for production.
- `trustServerCertificate: true` in the connection options — production imports the regional RDS CA bundle.
- No API authentication — a JWT authoriser on the HTTP API belongs in front before real exposure.
- State backend is local — an encrypted, access-controlled S3 backend is required before any shared use, because Terraform state contains the generated database password in plaintext.
- Express Edition is single-AZ. Any availability requirement means Standard Edition and a larger instance class.
